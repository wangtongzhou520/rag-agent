# CI 质量门禁

> **当前状态（2026-09-13）**：工作流文件 `.github/workflows/*.yml` **未纳入版本控制**，
> 远端仓库未启用 GitHub Actions。本文描述的门禁内容全部可在本地按第 2 节的命令执行；
> 工作流文件保留在本机 `.github/workflows/` 目录（已被 `.gitignore` 忽略），
> 需要启用远端自动化时，可在 GitHub 网页上直接新建，或改用 SSH/带 `workflow` 权限的凭据推送。

## 1. 目标与边界

CI 用于在合并前阻止代码质量、依赖兼容性、接口行为和页面流程回退。门禁分成两类：

1. `Quality Gate` 是确定性门禁，每次 push、pull request 和手动触发都会执行；
2. `Live RAG Quality Gate` 是外部环境门禁，只允许手动触发，分别运行事实问答与无答案安全套件，
   避免模型费用和供应商网络波动阻塞普通提交。

Elasticsearch、LightRAG 和 WebSearch 当前仍是可选检索增强项，不作为基础 CI 的服务依赖。

## 2. 确定性门禁

工作流文件：`.github/workflows/quality.yml`。

| Job                              | 运行环境                                             | 检查内容                                                   |
| -------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------- |
| Backend / Linux x64              | `ubuntu-latest`                                      | `uv sync --frozen`、Ruff、非集成 pytest                    |
| Backend / Apple Silicon          | `macos-14`（ARM64）                                  | 同一锁文件安装、Ruff、非集成 pytest                        |
| PostgreSQL and Redis integration | Ubuntu + `pgvector/pgvector:pg16` + `redis:7-alpine` | 真实 PG/pgvector、队列、入库、检索、Redis 多实例一致性测试 |
| Frontend                         | Ubuntu + Node.js 22                                  | `npm ci`、lint、typecheck、Vitest、生产构建、Chromium E2E  |
| Container build                  | Ubuntu + Docker Compose                              | compose 配置校验、后端/前端镜像构建、六服务健康启动与代理链路验收 |

`Container build` Job 使用 `.env.docker.example` 生成临时 `.env.docker`，先做
`docker compose config -q` 解析校验，再构建 `ragent-backend` 与 `ragent-frontend` 镜像，
以 `up -d --wait` 拉起六个服务后验证直连健康检查、Nginx 代理路径、业务接口与 uploads 卷可写，
最后 `down -v` 回收资源。失败时输出各服务末尾日志便于定位。该 Job 守护 Dockerfile、锁文件、
`compose.yaml` 与 `frontend/nginx.conf` 的漂移，部署细节见 `10-容器化部署.md`。

Apple Silicon Job 专门守卫本地开发机对应的平台依赖，尤其用于尽早发现 Python 原生依赖或 wheel
平台约束问题。Docker 集成测试放在 Linux Job，因为 GitHub Actions 的 macOS ARM64 Runner 不支持
嵌套虚拟化。

所有依赖都从版本锁文件安装：Python 使用 `uv.lock`，前端使用 `package-lock.json`。任何安装、检查、
测试或构建步骤失败，工作流都会失败。重复推送同一分支时，旧的确定性门禁会自动取消。

## 3. 真实 RAG 门禁

工作流文件：`.github/workflows/rag-quality.yml`。

运行前需要：

- 部署一个启用了 `eval.enabled` 的隔离测试环境；
- 将 `evals/corpus/` 导入 `m5_quality_baseline`，等待文档向量化成功；
- 若部署启用了认证，在 GitHub Repository Secret 中配置 `RAGENT_EVAL_TOKEN`，值为完整的
  `Authorization` 请求头原值；未启用认证时不需要配置该 Secret。

在 GitHub Actions 页面选择 `Live RAG Quality Gate`，点击 `Run workflow` 并填写：

- `base_url`：部署后的 API 根地址，必须包含 `/api/ragent`；
- `collection`：隔离评测集合，默认 `m5_quality_baseline`；
- `seed_corpus`：全新环境置 `true`，先由 `scripts/seed_eval_corpus.py` 建库、导入
  `evals/corpus` 并等待向量化完成；已有语料的环境保持 `false`，该 Job 会被跳过；
- `suite`：`all` 并行运行两套评测，`quality` 只运行 42 题事实问答集，`unanswerable` 只运行
  8 题无答案安全集；发布候选默认使用 `all`；
- `include_answers`：仅控制事实问答 Job；关闭时只验证检索，开启时同时调用 Chat 模型并验证答案
  关键事实；
- `judge_answers`：仅控制事实问答 Job；开启时隐含生成答案并额外运行语义裁判。无答案 Job 始终生成
  答案和运行语义裁判，并以正确拒答率 ≥ 0.80 作为硬门槛。

两个 Job 独立执行，因此一套失败不会阻止另一套完成取证；任一实际执行的 Job 失败都会使整个工作流
失败。事实问答报告以 `quality-<commit sha>` 发布，无答案报告以 `unanswerable-<commit sha>` 发布，
构建产物分别为 `rag-quality-answerable` 与 `rag-quality-unanswerable`，保留 30 天。Token 只通过
Secret 注入，不写入数据库或报告。

暂不配置定时执行。等测试环境地址、评测知识库和模型配额稳定后，再增加夜间 schedule；普通 PR
仍只运行确定性门禁。

## 4. 分支保护建议

在仓库分支保护规则中将以下检查设为 Required：

- `Backend (Linux x64)`；
- `Backend (Apple Silicon)`；
- `PostgreSQL and Redis integration`；
- `Frontend`。

`Live RAG Quality Gate` 第一阶段不设为每个 PR 的 Required Check。发布候选版本时手动选择 `all`，
并为事实问答开启答案与语义裁判；两个 Job 都通过后再发布。

## 5. 本地等价检查

```bash
uv sync --frozen --python 3.13
uv run ruff check .
uv run pytest -m "not integration" -q

RAGENT_RUN_INTEGRATION=1 \
RAGENT_DATASOURCE__PASSWORD='<local-password>' \
uv run pytest -m integration -q

cd frontend
npm ci
npm run lint
npm run typecheck
npm run test
npm run build
PLAYWRIGHT_PORT=45173 npm run e2e
```

本地真实质量评测仍按 `evals/README.md` 执行。API Token 和模型 Key 只放在进程环境变量或 CI
Secret 中，禁止提交到仓库。
