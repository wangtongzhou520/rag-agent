## 3. 待办批次

### B1 远程定时刷新（建议下一批）

**目标**：URL 源文档按 cron 周期自动重抓、比对变更、重新入库，全过程可观测、可恢复。

**现状证据**：

- 文档表只有 `schedule_enabled` / `schedule_cron` 两列（`app/knowledge/models.py:71`），
  没有 `t_knowledge_document_schedule` 与 exec 表，`app/worker.py` 里也没有任何 schedule 任务；
- 依赖里没有 cron 库（`pyproject.toml` 无 croniter 等），需要自研解析或新增依赖；
- 设计基线是 `docs/03-入库管线与文档处理.md` §10（扫描器 10s、批 20、版本号防旧任务覆盖、
  ETag → Last-Modified → SHA-256 三级变更检测、状态机写回与卡死恢复）。

**实施要点**：

1. 新增表：`t_knowledge_document_schedule`（文档、cron、version、enabled、next_run_time、
   last_etag、last_modified、last_content_hash、last_success_time、last_error）与
   `t_knowledge_document_schedule_exec`（每次执行记录）；沿用 `create_all`，
   但**已有库需要 `ensure_*` 兼容函数**（参考 `app/rag/intent/orm.py` 的
   `ensure_intent_audit_columns` 模式，`create_all` 不会给已有表加列）。
2. `CronScheduleHelper`：`next_run_time(cron, from)` 与最小间隔校验（≥60s）。
3. worker 内两个定时器：`scan_due_schedules`（10s，`FOR UPDATE SKIP LOCKED` 抢到期 schedule、
   推进 `next_run_time`、入队 `schedule-refresh` 任务）与复用现有 `recover_stuck`。
4. `ScheduleRefreshProcessor`：按 §10 的 INIT → … → FILE_SWITCHED 阶段机实现变更检测与写回，
   幂等与版本校验必须走任务 payload 里的 `scheduleVersion`。
5. API：文档保存时的 `upsertSchedule` / `syncScheduleIfExists`，以及管理端查询执行记录；
   前端文档表单增加 cron 配置入口（`frontend/src/features/knowledge/**`）。

**验收标准**：

- [ ] 给一个 URL 文档配置 `*/1 * * * *`（测试用更短周期时走注入的时钟），到期后 worker 自动重抓；
- [ ] 远端内容未变化时 exec 记为 `skipped`，不重新分块；
- [ ] 远端内容变化时文档 chunk 被替换（`replaceDocument` 语义），且旧文件被清理；
- [ ] cron 非法、周期小于 60s、文档非 URL 时给出明确入参错误；
- [ ] 模拟 worker 崩溃：重启后未完成任务被恢复为 pending 或按最大重试置 failed，无重复执行；
- [ ] 单元测试覆盖 cron helper、版本不匹配跳过、三级变更检测；集成测试覆盖一次完整刷新。

**风险**：新增两张表与状态机，跨表一致性要求高；建议先只支持"文档已存在且为 URL 源"的路径，
不支持新建文档时自动开刷新。

**规模**：中大（后端为主 + 少量前端）。

### B2 Pipeline 线上接入（`processMode=pipeline`）

**目标**：知识库文档分块可选择走可编排 Pipeline（而非固定内核），支持按文档类型套用不同流程。

**现状证据**：`process_mode` 字段已存在（`app/knowledge/models.py:63`，默认 `chunk`），
`KnowledgeService` 里写死 `process_mode="chunk"`（`app/knowledge/service.py:221`）；
`docs/03` §11.1 明确"`processMode=pipeline` 在功能完成前显式返回未开放，不得静默降级"。

**实施要点**：

1. 文档创建/更新接口接受 `processMode` 与 `pipelineId`，服务端校验 Pipeline 存在且节点合法；
2. worker 的 `chunk-document` 处理器按 `process_mode` 分流：pipeline 分支用
   `skipIndexerWrite=true` 执行 `IngestionEngine`，由调用方事务统一写向量与 chunk 表；
3. 失败语义与现有 chunk 路径一致（文档 `failed` + `errorMessage` + 节点日志落 `t_ingestion_task_node`）；
4. 灰度：默认仍为 `chunk`，仅在显式指定时走 pipeline，保留回退开关。

**验收标准**：

- [ ] 指定 `processMode=pipeline` 的文档能完成入库，chunk 与向量内容与固定内核等价（同一语料对比）；
- [ ] Pipeline 节点失败时文档置 failed，错误可读且可在管理台看到节点级日志；
- [ ] 未指定 pipeline 时行为与现在完全一致（回归测试）；
- [ ] 前端文档表单支持选择处理模式与 Pipeline。

**风险**：触碰线上主链路，必须保证默认路径零行为变化；建议先做"等价性对比测试"再开放。

**规模**：中大。

### B3 分块体系完整化

**目标**：从"通用打包 + 句界切分"升级为按 Block 类型分发的完整分块体系，并补齐章节与来源信息。

**现状证据**：

- `app/core/chunk/service.py` 目前是单一 `ChunkingService`：标题栈 + 同节打包 + `split_text`；
- 缺 `BlockAwareChunkerDispatcher` 与七类 chunker（Heading/Paragraph/Table/HtmlTable/List/Code/Image）；
- 缺 `ChunkAssembler.restore`（编辑后重建章节路径）与向量文本前缀规则；
- `TextSplitter` 未实现 URL 断行修复与 CJK 软换行合并；
- 验收发现：PDF 解析器只产出 `ParagraphBlock`，因此**章节路径恒为空**、呈现"一页一块"。

**实施要点**：按 `docs/03` §6 实现分发表与各类型 handler；为 PDF 增加轻量标题启发式
（字号/行首模式识别）或明确降级策略；补齐 `TextSplitter` 两个增强。

**验收标准**：

- [ ] Markdown/Excel 语料的 chunk 带正确章节路径，表格块不被拦腰切断；
- [ ] PDF 语料章节路径要么可用、要么在文档中明确标注"PDF 无结构识别"的降级行为；
- [ ] 编辑 chunk 后 `restore` 能重建章节路径与新向量文本；
- [ ] 现有 `tests/test_ingestion_core.py` 全部通过，且新增各类型 chunker 单测。

**规模**：中。

### B4 意图配置与默认数据

**目标**：意图节点支持自定义提参模板；首启即有可用的 SYSTEM 意图，避免"自我介绍被当知识问题"。

**现状证据**：

- `IntentNodeRecord` 无 `param_prompt_template` / `prompt_snippet` 字段（`app/rag/intent/orm.py:10`）；
- 首次部署意图树为空 → 闲聊/自我介绍落到检索分支并返回固定文案（2026-09-12 实测）；
- 分类器阈值 `0.6`（`classifier.py:26`）与解析器 `0.35`（`resolver.py:11`）双标准，
  且 `docs/02` 声称的"每子问题保底 1 个最高分意图（capTotalIntents）"在代码中不存在。

**实施要点**：

1. 新增两列（需 `ensure_*` 兼容函数，方法同 B1）+ 管理端字段 + MCP 提参时优先使用自定义模板；
2. `promptSnippet` 注入生成上下文（工具结果之外的人设补充片段）；
3. 首启内置一条 SYSTEM 叶子（`ensure_builtin_intents`），并把双阈值收敛为一处配置；
4. 决策"保底 top-1"是否补实现：若补，需同步更新无答案安全集的拒答判定。

**验收标准**：

- [ ] 新环境首次启动后问"你是谁"能走 SYSTEM 分支并正常自我介绍；
- [ ] 自定义提参模板生效（用例：同一工具不同模板产出不同参数）；
- [ ] 阈值只有一处权威来源，`docs/02` 与实现一致；
- [ ] 无答案安全集拒答率仍 ≥ 0.80。

**规模**：中。

### B5 大文件与扫描件

**目标**：支持大文件上传与扫描版 PDF 入库。

**现状证据**（来自 `docs/12` 的真实语料预检）：

- Nginx `client_max_body_size 100m`，192MB 的 PDF 在代理层被 413 拒绝；
- 86MB / 192MB 两本均为扫描版，`pypdf` 抽取 0 字符 → 分块失败；
- 解析器矩阵缺 MinerU 与图片/SVG + VLM 路径（`docs/03` §5.5、§5.6）。

**实施要点**：分片/断点续传上传或提高上限并评估内存；接入 MinerU（或等价 OCR）解析器与
并发信号量；图片解析走 VLM 图生文 + 资产桶。

**验收标准**：

- [ ] 200MB 级文件可上传（分片或调整上限），失败时前端有明确提示；
- [ ] 扫描版 PDF 经 OCR 后可检索（用 `docs/12` 的两本扫描书验证）；
- [ ] OCR 并发受信号量保护，超限按 429 降级。

**风险**：依赖外部 OCR/VLM 服务与配额；成本与耗时需先评估。

**规模**：大（外部依赖为主）。
